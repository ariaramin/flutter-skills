## Technical resolutions checked against official documentation

- **Controller attachment:** a `ScrollController` can control multiple scrollables. Operations such as reading `offset` require a single attachment. Check the operation's contract rather than imposing one controller per scrollable universally. [ScrollController API](https://api.flutter.dev/flutter/widgets/ScrollController-class.html).
- **Pattern context:** exhaustive checking and pattern failure depend on the construct and matched type. Keep declaration failure distinct from an unsuccessful `if-case` or switch match. [Branches](https://dart.dev/language/branches), [pattern types](https://dart.dev/language/pattern-types).
- **Dart API design:** prefer meaningful absence and error contracts. Effective Dart's advice about nullable futures/streams/collections is narrower than a ban on all null results. Parameter clarity and project formatting matter more than generic argument or line quotas. [Effective Dart design](https://dart.dev/effective-dart/design), [dart format](https://dart.dev/tools/dart-format).
- **Local state and error boundaries:** `setState` remains a supported local-state mechanism. Preserve framework and uncaught asynchronous error reporting according to where errors occur; a mandatory zone wrapper is not the complete Flutter error model. [setState API](https://api.flutter.dev/flutter/widgets/State/setState.html), [Flutter error handling](https://docs.flutter.dev/testing/errors).
- **Visual changes:** preserve existing design tokens and verify semantics, text scaling and contrast. A source's aesthetic preference does not authorize changing a behavior-preserving refactor's visual contract. [Flutter accessibility](https://docs.flutter.dev/ui/accessibility-and-internationalization/accessibility).

Package choices and app-specific security/storage behavior still require the actual project's versions and platform contracts. Neither these summaries nor this audit establish application runtime performance.

## Did the comparison justify more runtime instructions?

Most useful practices were already covered. Two candidate gaps deserved a behavioral check: bootstrapping tests when construction performs I/O/time reads, and checking generated/native consumers before deleting an apparently unused compatibility decoder.

A fresh independent agent used the unchanged skill on a time-constrained exporter-cleanup scenario. It preserved the decoder, inspected generated/native registration, sought a fixture-based observable boundary, proposed only the minimal database/clock seam if needed, preserved production ordering/defaults, and stopped when verification could not be established. It also explicitly avoided editing generated registrations. This supplied no demonstrated failure requiring another universal rule.

Consequently this follow-up changes research traceability, not the runtime workflow. The new scenario is a qualitative applicability check, not an additional old-versus-new benchmark or proof of implemented compatibility. Original comparisons remain 9/9 assertions for both versions, without demonstrated incremental benefit. Human review and real application/device checks remain open.
