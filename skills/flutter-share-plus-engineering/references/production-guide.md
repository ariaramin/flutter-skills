# Purpose

This skill governs production implementation, architecture, debugging, review, testing, security, privacy, and performance optimization for cross-platform sharing through `share_plus`.

Use it for:

- sharing text
- sharing URLs/URIs
- sharing images
- sharing PDFs
- sharing generated documents
- sharing audio/video
- sharing one or several files
- sharing in-memory generated content
- iPad share popovers
- macOS share positioning
- Web Share API integration
- Web fallback downloads
- Web email fallback
- Windows sharing
- Linux email fallback
- share-result interpretation
- temporary-file management
- large-file memory optimization
- migration from deprecated `Share.*` APIs
- receiver compatibility
- privacy/security review
- testing native share behavior

This skill treats sharing as a transition across an application trust boundary.

Once content is handed to the platform share mechanism, the application does not control what the selected destination does with it.

# Core Principles

1. **Use the current `SharePlus.instance.share(ShareParams(...))` API.**

2. **Do not assume platform capability parity.**

3. **Prefer an existing file-backed `XFile` for an existing large file.**

4. **Do not call `readAsBytes()` merely to re-wrap an existing file for sharing.**

5. **Do not claim file sharing is zero-copy. Android currently copies shared files into its own share cache.**

6. **Use `XFile.fromData` for genuinely in-memory/generated content, not as a default file-sharing pattern.**

7. **Keep expensive payload generation outside widget `build()` methods.**

8. **Keep sharing user-initiated. This is mandatory for native Web Share because browsers require transient user activation.**

9. **Provide an accurate `sharePositionOrigin` on iPad/macOS when a source widget is available.**

10. **Do not interpret `ShareResultStatus.success` as confirmed external delivery.**

11. **Treat `subject`, `title`, MIME hints, and multi-attachment behavior as receiver-dependent.**

12. **Use the most accurate MIME type and a meaningful filename/extension.**

13. **Never share secrets or credentials.**

14. **Treat private/signed URLs as bearer-like information once shared.**

15. **Prevent overlapping share invocations from one control.**

16. **Dismissal is normal user behavior, not an application failure.**

17. **Web download/email fallback must be surfaced as fallback behavior, not falsely described as a successful native share.**

18. **Do not add obsolete Android storage permissions or manual FileProvider configuration solely for current `share_plus`.**

19. **Test receiver behavior on real target devices and applications.**

20. **Optimize payload generation and materialization before micro-optimizing the `share()` invocation itself.**

# Package Architecture

Conceptually:

```text
Flutter UI
   |
   v
SharePlus.instance.share(...)
   |
   v
SharePlatform
   |
   +----------------------+----------------------+----------------------+
   |                      |                      |
   v                      v                      v
Method channel          Web/Dart              Desktop Dart/native
   |                    implementation         implementations
   |
   +--> Android Intent / Android Sharesheet
   |
   +--> iOS UIActivityViewController
   |
   +--> macOS NSSharingServicePicker
```

The result is then controlled by:

```text
operating system
        |
        v
selected receiver application
```

The receiver may:

- ignore `subject`
- ignore `title`
- reject an attachment
- reject mixed attachment types
- transform content
- strip text
- change filenames
- display its own editor
- cancel after selection
- fail after receiving the share request

`share_plus` cannot guarantee receiver correctness.

# Native vs Browser Behavior

Android uses native share intents.

iOS uses:

```text
UIActivityViewController
```

macOS uses:

```text
NSSharingServicePicker
```

Web uses:

```text
navigator.canShare()
navigator.share()
```

when supported.

Linux currently uses a:

```text
mailto:
```

fallback for text/URI.

Modern Windows versions use the native Windows sharing UI. Older Windows versions fall back to email for text/URI and cannot share files.

# Current API

The primary current API is:

```dart
final ShareResult result =
    await SharePlus.instance.share(
  ShareParams(
    text: 'Hello',
  ),
);
```

Current `ShareParams` constructor:

```dart
ShareParams({
  String? text,
  String? subject,
  String? title,
  XFile? previewThumbnail,
  Rect? sharePositionOrigin,
  Uri? uri,
  List<XFile>? files,
  List<String>? fileNameOverrides,
  bool downloadFallbackEnabled = true,
  bool mailToFallbackEnabled = true,
  List<CupertinoActivityType>? excludedCupertinoActivities,
})
```

---

# Current Parameter Rules

At least one of these MUST be present:

```text
text
uri
files
```

Invalid:

```dart
ShareParams();
```

Invalid:

```dart
ShareParams(
  text: '',
);
```

Invalid:

```dart
ShareParams(
  text: 'Visit this page',
  uri: Uri.parse('https://example.com'),
);
```

`uri` and `text` are mutually exclusive.

If a URL needs accompanying prose, use `text`:

```dart
ShareParams(
  text: 'Read this article: https://example.com/article',
);
```

instead of specifying both `text` and `uri`.

An empty files list is invalid.

If `fileNameOverrides` is supplied, it MUST contain the same number of entries as `files`.

# Deprecated APIs

Do not generate new code using:

```dart
Share.share(...)
Share.shareUri(...)
Share.shareXFiles(...)
```

These static APIs were deprecated by the 11.0 refactor.

Migrate:

```dart
Share.share(
  'Hello',
);
```

to:

```dart
SharePlus.instance.share(
  ShareParams(
    text: 'Hello',
  ),
);
```

Migrate:

```dart
Share.shareXFiles(
  files,
);
```

to:

```dart
SharePlus.instance.share(
  ShareParams(
    files: files,
  ),
);
```

`ShareParams.previewThumbnail` currently exists in the public API and is documented as Android-only.

# Basic Text Sharing

```dart
import 'package:share_plus/share_plus.dart';

Future<ShareResult> shareText(
  String text,
) {
  if (text.trim().isEmpty) {
    throw ArgumentError.value(
      text,
      'text',
      'Share text must not be empty.',
    );
  }

  return SharePlus.instance.share(
    ShareParams(
      text: text,
    ),
  );
}
```

Unicode, multiline text, emoji, and normal Dart strings can be shared.

Example:

```dart
await SharePlus.instance.share(
  ShareParams(
    text: '''
Hello 👋

Here is the information you requested:
https://example.com
''',
  ),
);
```

# Large Text

`share_plus` does not document one universal maximum text length.

Do not invent one.

However, very large strings are a poor share-sheet payload because:

- platform IPC mechanisms have practical limits
- email/message/social targets can impose their own limits
- targets may truncate content
- copy/preview UI becomes poor
- a document-like payload is usually better represented as a file

For substantial documents, consider:

```text
plain text file
PDF
hosted URL
```

based on the intended recipient experience.

---

# Text Localization

Share the final localized user-visible string.

Do not share internal localization keys:

```text
share.report.message
```

unless that is intentionally the content.

The receiver gets content, not your Flutter localization context.

# URI Sharing

Current API:

```dart
await SharePlus.instance.share(
  ShareParams(
    uri: Uri.parse(
      'https://example.com/article/42',
    ),
  ),
);
```

On iOS, URI sharing gets special URL metadata behavior from the platform share controller.

On most other targets the URI behaves similarly to text.

---

# URL as URI vs Text

## Use `uri`

When:

- the content is fundamentally one URL
- iOS link-preview metadata is desirable
- no explanatory text is needed

Example:

```dart
ShareParams(
  uri: Uri.parse(
    'https://example.com/product/123',
  ),
);
```

## Use `text`

When:

- explanatory prose accompanies the link
- compatibility with text-oriented receivers matters
- several links are included

Example:

```dart
ShareParams(
  text: '''
Check out this product:
https://example.com/product/123
''',
);
```

Do not specify both.

---

# Custom URI Schemes

A `Uri` object can represent custom schemes, but that does not mean receiving applications support them.

Example:

```text
myapp://item/123
```

may be useless outside applications that understand that scheme.

When sharing a deep link externally, usually include an HTTPS fallback or universal/app-link URL if product architecture provides one.

Do not share internal-only callback URIs containing:

- OAuth codes
- Auth tokens
- PKCE values
- session identifiers

# Existing File Sharing

Prefer a path-backed `XFile` when a file already exists.

Example:

```dart
import 'package:share_plus/share_plus.dart';

Future<ShareResult> sharePdf(
  String path,
) {
  return SharePlus.instance.share(
    ShareParams(
      files: <XFile>[
        XFile(
          path,
          mimeType: 'application/pdf',
        ),
      ],
    ),
  );
}
```

This avoids first reading the entire PDF into the Dart heap.

---

# File Existence

Validate files before launching expensive preparation if the path can become stale.

Native example:

```dart
import 'dart:io';

import 'package:share_plus/share_plus.dart';

Future<ShareResult> shareExistingPdf(
  String path,
) async {
  final File file = File(path);

  if (!await file.exists()) {
    throw StateError(
      'The PDF no longer exists.',
    );
  }

  return SharePlus.instance.share(
    ShareParams(
      files: <XFile>[
        XFile(
          path,
          mimeType: 'application/pdf',
        ),
      ],
    ),
  );
}
```

Do not run `dart:io` code on Web.

# Mixed File Types

Avoid mixing unrelated types unless the UX requires it.

Example:

```text
image/jpeg
application/pdf
video/mp4
```

On Android the plugin reduces unrelated MIME types to:

```text
*/*
```

which can reduce target compatibility.

Prefer coherent share groups when possible.

---

# MIME Types

Use accurate MIME types.

Common examples:

```text
text/plain
image/jpeg
image/png
application/pdf
video/mp4
application/octet-stream
```

Use:

```text
application/octet-stream
```

only when no more accurate type is available.

Incorrect:

```dart
XFile(
  pdfPath,
  mimeType: 'image/png',
);
```

Correct:

```dart
XFile(
  pdfPath,
  mimeType: 'application/pdf',
);
```

---

# MIME Inference

When `XFile.mimeType` is absent on method-channel platforms, current plugin code attempts to infer MIME from the path.

If inference fails it uses:

```text
application/octet-stream
```

Do not rely exclusively on inference when your application already knows the content type.

Generated files should normally supply it explicitly.

Good:


Good:


Poor:


Poor:


# `fileNameOverrides`

Example for generated pathless data:

```dart
final XFile file = XFile.fromData(
  bytes,
  mimeType: 'application/pdf',
);

await SharePlus.instance.share(
  ShareParams(
    files: <XFile>[file],
    fileNameOverrides: const <String>[
      'report.pdf',
    ],
  ),
);
```

This is an important use case because generated `XFile.name` is ignored by many native paths.

---

# `fileNameOverrides` Native Caveat

Current method-channel implementation returns an already path-backed `XFile` without renaming it.

Therefore this:

```dart
ShareParams(
  files: <XFile>[
    XFile(
      '/cache/a8b713.bin',
      mimeType: 'application/pdf',
    ),
  ],
  fileNameOverrides: const <String>[
    'report.pdf',
  ],
)
```

should **not** be treated as a guaranteed native rename operation.

If a precise visible native filename matters, materialize or copy the export with the desired actual filename first.

# In-Memory `XFile`

Current API supports:

```dart
XFile.fromData(
  bytes,
  mimeType: 'text/plain',
)
```

Example:

```dart
import 'dart:convert';

import 'package:share_plus/share_plus.dart';

Future<ShareResult> shareGeneratedTextFile(
  String text,
) {
  final XFile file = XFile.fromData(
    utf8.encode(text),
    mimeType: 'text/plain',
  );

  return SharePlus.instance.share(
    ShareParams(
      files: <XFile>[file],
      fileNameOverrides: const <String>[
        'notes.txt',
      ],
    ),
  );
}
```

This is appropriate for small generated payloads.

# How In-Memory Files Are Materialized

On method-channel targets, a pathless `XFile` is currently processed roughly as:

```text
XFile
  |
  | readAsBytes()
  v
Dart byte buffer
  |
  | writeAsBytes()
  v
temporary file
  |
  v
native share implementation
```

On Android, that temporary file is then additionally copied into:

```text
<app cache>/share_plus/
```

before `FileProvider` exposes it to other applications.

Do not call this a zero-copy path.

---

# `XFile.fromData` Performance

If a 500 MB video already exists at:

```text
/cache/export.mp4
```

bad:

```dart
final bytes =
    await File('/cache/export.mp4').readAsBytes();

final file = XFile.fromData(
  bytes,
  mimeType: 'video/mp4',
);

await SharePlus.instance.share(
  ShareParams(
    files: <XFile>[file],
  ),
);
```

This can require hundreds of megabytes of Dart heap plus another temporary disk write.

Preferred:

```dart
await SharePlus.instance.share(
  ShareParams(
    files: <XFile>[
      XFile(
        '/cache/export.mp4',
        mimeType: 'video/mp4',
      ),
    ],
  ),
);
```

Android will still make its platform share-cache copy, but Dart does not first duplicate the entire file into memory.

---

# Multiple In-Memory Files

Current method-channel implementation materializes several pathless files using `Future.wait`.

That means several large files can be read/written concurrently.

Avoid patterns such as:

```text
10 × 100 MB in-memory attachments
```

unless memory and I/O behavior has been explicitly measured.

For large multi-file sharing, prefer actual file-backed `XFile`s.

---

# Web File Memory

Current Web implementation converts `XFile`s into browser `File` objects by calling:

```text
readAsBytes()
```

for each attachment.

Therefore even a path-backed abstraction on Web does not give the same file-path efficiency as native platforms.

A browser share of:

```text
500 MB + 500 MB + 500 MB
```

can be a poor design regardless of Dart API elegance.

Consider:

- sharing a hosted URL
- reducing attachment size
- reducing attachment count
- explicit download UX

depending on product semantics.

---

# Temporary Files

The package documentation explicitly warns that `XFile.fromData` may create temporary files.

The operating system may reclaim application cache/temp storage as space is needed.

That is not the same as:

```text
file is guaranteed to disappear immediately after share sheet closes
```

Do not assume immediate cleanup.

---

# Safe Temporary-File Strategy

When cleanup control matters, explicitly create an application-owned temporary export directory.

Optional helper using `path_provider`:

```dart
import 'dart:io';
import 'dart:typed_data';

import 'package:path_provider/path_provider.dart';

final class ShareExportStore {
  static const String _folderName =
      'my_app_share_exports';

  Future<Directory> _directory() async {
    final Directory root =
        await getTemporaryDirectory();

    final Directory directory = Directory(
      '${root.path}'
      '${Platform.pathSeparator}'
      '$_folderName',
    );

    if (!await directory.exists()) {
      await directory.create(
        recursive: true,
      );
    }

    return directory;
  }

  Future<File> writeBytes({
    required String fileName,
    required Uint8List bytes,
  }) async {
    final Directory directory =
        await _directory();

    final File file = File(
      '${directory.path}'
      '${Platform.pathSeparator}'
      '$fileName',
    );

    return file.writeAsBytes(
      bytes,
      flush: true,
    );
  }

  Future<void> clear() async {
    final Directory directory =
        await _directory();

    if (await directory.exists()) {
      await directory.delete(
        recursive: true,
      );
    }
  }
}
```

This helper is native-only because it uses `dart:io`.

Use a Web-specific export path for browsers.

---

# Do Not Delete the Entire Temporary Directory

Bad:

```dart
final directory =
    await getTemporaryDirectory();

await directory.delete(
  recursive: true,
);
```

Other plugins/application subsystems may also use the application's temp directory.

Preferred:

```text
create your own share-export subdirectory
clean only that directory
```

---

# Android's Own Share Cache

Current Android implementation uses:

```text
<app cache>/share_plus
```

and clears previous entries when preparing a new share.

The latest Android share can remain until:

- a later share clears it
- application cache is cleared
- OS storage management reclaims it

Do not build business logic depending on that implementation detail.

It is version-sensitive.

---

# Large File Performance

For large files, optimize this order:

```text
1. avoid unnecessary generation
2. avoid reading existing file into Dart heap
3. avoid duplicate export copies under app control
4. keep attachment count bounded
5. use appropriate compression if product semantics allow
6. invoke share_plus with file-backed XFiles
```

The native share sheet invocation itself is usually not the expensive part.

# CPU vs Memory vs Disk

## CPU

Typically dominated by:

- PDF rendering
- image encoding
- video transcoding
- archive compression
- screenshot composition

## Dart memory

Typically dominated by:

- `readAsBytes()`
- generated image buffers
- PDF byte buffers
- `XFile.fromData`
- Web browser-file materialization

## Disk

Typically dominated by:

- generated export files
- pathless `XFile` materialization
- Android's share-cache copy

## Native memory

Can include:

- image decoding for previews
- platform share metadata
- receiver application processing

These are distinct costs.

# Android Guidance

Current Android implementation uses:

```text
ACTION_SEND
ACTION_SEND_MULTIPLE
Intent.createChooser
FileProvider
content:// URIs
temporary URI grants
```

This is the correct modern Android sharing model.

# Android File Handling

Current flow:

```text
existing app-readable file
     |
     v
copy to cacheDir/share_plus
     |
     v
FileProvider content:// URI
     |
     v
grant URI permission
     |
     v
Android Sharesheet
```

In 13.3.0, the blocking disk preparation is performed on an Android I/O dispatcher rather than the platform main thread.

That improves UI responsiveness but does not eliminate disk I/O.

---

# Android MIME Selection

One file:

```text
exact MIME if known
otherwise fallback
```

Several files:

```text
same MIME
    -> exact MIME

same family
    -> family/*

unrelated families
    -> */*
```

Avoid `*/*` when possible.

---

# Android Permissions

Current `share_plus` does not require consumers to add broad:

```text
READ_EXTERNAL_STORAGE
WRITE_EXTERNAL_STORAGE
MANAGE_EXTERNAL_STORAGE
READ_MEDIA_*
```

permissions solely to share a file that the application can already read.

Do not copy old storage-permission tutorials.

Separate concerns:

```text
share_plus permission need
```

from:

```text
permission required by your own code to acquire/read a file
```

For example, a media-picker workflow may have its own permissions or system-picker model.

---

# Android FileProvider

Do not manually create an old custom FileProvider configuration solely for current `share_plus`.

The plugin handles its own file sharing through `FileProvider`.

Manual providers may still be appropriate for other application features, but that is independent.

---

# Android Receiver Result

Android can report which target was selected to the chooser mechanism.

That means:

```text
target selected
```

not:

```text
message delivered
post published
recipient opened file
```

Never treat it as delivery confirmation.

---

# iOS Guidance

iOS uses:

```text
UIActivityViewController
```

Files are provided as file URLs for the actual share operation.

For images, current plugin code can decode the file to build previews/thumbnails.

Therefore extremely large source image dimensions can still cause native image-decoding memory pressure.

If the product does not need the full-resolution image, resize/compress it before sharing.

Do not recompress an already suitable image merely as ritual.

---

# iOS URI Sharing

`ShareParams(uri: ...)` is particularly useful on iOS because the system can fetch page metadata for share-sheet presentation.

Use this for pure links.

If accompanying prose is needed, use `text` instead.

# iPad Popover

On iPad, `UIActivityViewController` is presented as a popover.

Current `share_plus 13.3.0` falls back to a small center anchor if no valid origin is supplied.

Older releases could throw or produce unusable UI.

Even on 13.3.0, an accurate origin remains the preferred UX.

---

# Correct `sharePositionOrigin`

Use the RenderBox belonging to the actual share button/source control.

```dart
import 'package:flutter/material.dart';
import 'package:share_plus/share_plus.dart';

Rect? shareOriginForContext(
  BuildContext context,
) {
  final RenderObject? renderObject =
      context.findRenderObject();

  if (renderObject is! RenderBox ||
      !renderObject.attached ||
      !renderObject.hasSize) {
    return null;
  }

  final Size size = renderObject.size;

  if (size.width <= 0 ||
      size.height <= 0) {
    return null;
  }

  final Offset topLeft =
      renderObject.localToGlobal(
    Offset.zero,
  );

  return topLeft & size;
}
```

Usage:

```dart
Builder(
  builder: (BuildContext buttonContext) {
    return FilledButton(
      onPressed: () async {
        final Rect? origin =
            shareOriginForContext(
          buttonContext,
        );

        await SharePlus.instance.share(
          ShareParams(
            text: 'Hello',
            sharePositionOrigin: origin,
          ),
        );
      },
      child: const Text('Share'),
    );
  },
);
```

---

# Do Not Use Arbitrary Giant Origin Rectangles

Avoid:

```dart
MediaQuery.sizeOf(context) & Offset.zero
```

merely to satisfy old iPad crash workarounds.

An accurate source-control rectangle gives the system the intended popover anchor.

Current 13.3.0 has a center fallback if no valid origin exists.

# Async iPad Safety

If export generation occurs before sharing:

```dart
Future<void> prepareAndShare(
  BuildContext context,

  final XFile export =
      await generateExport();

    return;

  final Rect? origin =
```

- the widget may have moved
- orientation may have changed
- layout may have changed
- the widget may have been disposed

# Web Guidance

Web uses:

```text
navigator.canShare()
navigator.share()
```

when available.

The Web Share API:

- is not supported uniformly across all major browsers
- requires a secure context
- requires transient user activation
- can reject unsupported file types
- can be blocked by Permissions Policy
- can fail when another share operation is active

Do not assume desktop Chrome, Firefox, Safari, mobile Safari, Android Chrome, and Edge have identical capability.

# Web User Activation

Native Web Share MUST originate from transient user activation.

Good:

```dart
FilledButton(
  onPressed: () {
    SharePlus.instance.share(
      ShareParams(
        text: readyText,
      ),
    );
  },
  child: const Text('Share'),
);
```

Potentially problematic:

```dart
FilledButton(
  onPressed: () async {
    await Future<void>.delayed(
      const Duration(seconds: 5),
    );

    await SharePlus.instance.share(
      ShareParams(
        text: readyText,
      ),
    );
  },
  child: const Text('Share'),
);
```

The browser may no longer consider the call user-activated.

# Expensive Web Preparation

If a report takes several seconds to generate, prefer:

```text
Generate / Prepare
       |
       v
ready state
       |
       v
explicit Share button
       |
       v
SharePlus immediately
```

This preserves an explicit user gesture for the actual Web Share call.

Example UX:

```text
[Prepare report]

Preparing...

Report ready.

[Share report]
```

Do not hide a five-second export behind the final Web Share click and assume transient activation survives.

# Web Share File Capability

File sharing support is narrower than basic text/URL sharing.

`share_plus` calls:

```text
navigator.canShare(...)
```

before attempting Web Share.

If it returns false, fallback behavior applies.

Do not maintain a hardcoded browser-support list in application code unless the product has a tested compatibility requirement.

Use actual runtime behavior and test representative browsers.

---

# Web File Fallback

Default:

```dart
downloadFallbackEnabled: true
```

If browser native file sharing fails/unavailable, the plugin can trigger file downloads instead.

This:

```text
downloaded file
```

is not equivalent to:

```text
user shared file to another application
```

If that semantic difference matters, disable fallback:

```dart
ShareParams(
  files: files,
  downloadFallbackEnabled: false,
)
```

and expose a separate:

```text
Download
```

action in the UI.

# Web Text/URI Email Fallback

Current default:

```dart
mailToFallbackEnabled: true
```

When native Web Share cannot be used for text/URI, the implementation may open a:

```text
mailto:
```

URL.

Disable when email compose is not an acceptable fallback:

```dart
ShareParams(
  text: content,
  mailToFallbackEnabled: false,
)
```

Then handle the resulting failure with an explicit application fallback.

# Web Result Semantics

After `navigator.share()` resolves successfully, current Web `share_plus` returns:

```text
ShareResult.unavailable
```

because the plugin does not expose a meaningful target result there.

An `AbortError` can map to:

```text
dismissed
```

Do not write Web business logic requiring:

```text
ShareResultStatus.success
```

# Linux Guidance

Linux currently does not support file sharing through `share_plus`.

Files result in:

```text
UnimplementedError
```

Text/URI is implemented through an email:

```text
mailto:
```

fallback.

Therefore a product that promises:

```text
Share this PDF
```

on Linux needs another UX:

- save/export
- copy path
- open containing folder
- custom desktop integration

Do not silently pretend email-text fallback shared the PDF.

# Windows Guidance

Modern supported Windows versions use the native Windows sharing mechanism and support file sharing.

Older Windows versions fall back to email for text/URI.

Older Windows file sharing is unsupported.

Therefore if the product supports older Windows installations:

- test the actual minimum supported Windows build
- provide an explicit file-save fallback
- do not assume the pub.dev platform badge means every Windows version has identical capabilities

# Share Results

Current result:

```dart
final ShareResult result =
    await SharePlus.instance.share(
  ShareParams(
    text: 'Hello',
  ),
);
```

Contains:

```dart
result.status
result.raw
```

Statuses:

```text
success
dismissed
unavailable
```

---

# `success`

Means the platform/plugin observed an action considered successful enough to classify as:

```text
user selected an action
```

It does not universally mean:

```text
content delivered
content uploaded
message sent
post published
file saved
recipient opened
recipient accepted
```

---

# `dismissed`

Means the platform/plugin observed cancellation/dismissal where supported.

Do not show:

```text
"Sharing failed!"
```

for normal dismissal.

Usually do nothing.

---

# `unavailable`

Means:

```text
the platform cannot provide a meaningful user-action result
```

or an implementation has fallen back to a non-result share path.

It is not automatically an error.

---

# `raw`

`raw` can contain platform-specific information such as an activity/service identifier.

Do not build core business logic around the exact format of `raw`.

It can differ across:

- OS versions
- share targets
- plugin versions

Use it only for optional diagnostics/analytics after privacy review.

---

# Never Treat Share Result as Business Confirmation

Bad:

```dart
final ShareResult result =
    await SharePlus.instance.share(
  params,
);

if (result.status ==
    ShareResultStatus.success) {
  await backend.markInvitationDelivered();
}
```

Why:

The share API does not know whether an invitation was delivered.

Preferred:

```text
backend invitation
 -> authoritative delivery/acceptance state

share sheet
 -> optional user convenience
```

---

# Analytics Boundary

Safe analytics may record:

```text
share_initiated
share_target_selected
share_dismissed
share_result_unavailable
```

when useful and supported.

Do not log:

- complete shared text
- private filenames
- tokens
- signed private URLs
- personal document contents

And never label:

```text
ShareResultStatus.success
```

as:

```text
message_delivered
```

These fields are hints, not portable data contracts.

Intended as the share sheet/content title where supported.

Android uses it for chooser/title-related extras.

Web supplies a title to the Web Share API.

Receivers may ignore it.

---

# `subject`

Intended mainly as an email subject where supported.

Android supplies:

```text
EXTRA_SUBJECT
```

Apple/macOS services may use it.

Email fallbacks use it.

Third-party destinations may ignore it.

Current Web implementation chooses:

```text
subject ?? title
```

for the Web Share API's title.

Therefore if both are supplied, do not assume browser targets see the `title` field rather than `subject`.

This is an implementation detail and should be treated as version-sensitive.

# Image Compression

Compress/resize before sharing only when product requirements permit.

Reasons:

- reduce transfer size
- reduce disk copy
- reduce upload/receiver time
- reduce Web memory
- reduce native preview decode cost

Do not automatically recompress:

- already optimized files
- evidence images requiring exact fidelity
- archival originals
- assets whose quality must remain unchanged

# iOS Image Preview Cost

Current iOS implementation can decode image files to create share-sheet preview metadata.

A compressed 20 MB JPEG may decode into substantially more native memory depending on pixel dimensions.

Therefore image dimensions matter in addition to compressed file size.

- image compositing

- cryptographic packaging
- video processing

# Remote Files

There are three common architectures.

## Share hosted URL

Use when:

- recipient should open hosted content
- attachment is unnecessary
- URL remains accessible
- link semantics are intended

Advantages:

- minimal device disk/memory
- no download delay
- no duplicate file

Tradeoffs:

- needs network
- recipient depends on hosted availability/auth

---

## Share signed/private URL

Use when:

- temporary URL access is acceptable
- recipient should access hosted content

Risks:

- URL is bearer-like while valid
- recipient can forward it
- short expiry can break the share later
- long expiry increases exposure window

Never log the URL if it contains sensitive credentials/signatures.

---

## Download then share attachment

Use when:

- recipient needs a standalone file
- target apps expect an attachment
- hosted authentication would prevent recipient access
- content should remain usable independently of the server link

Costs:

- network download
- local disk
- possibly Android copy
- Web memory if then shared through Web Share

Cache the downloaded export if repeated sharing is likely and privacy permits.

---

# Signed URL Decision

A short expiry reduces exposure but increases the chance:

```text
recipient opens after expiration
```

A file attachment does not expire, but permanently leaves your control once shared.

Choose based on intended data lifecycle.

---

# Privacy and Security

Sharing is an outbound trust-boundary operation.

Assume:

```text
anything shared can leave your application permanently
```

# MUST NOT Share

- passwords
- access tokens
- refresh tokens
- OAuth authorization codes
- PKCE verifiers
- session cookies
- private API keys
- service credentials
- encryption keys
- private debug logs
- database credentials
- hidden internal URLs containing secrets

# Sensitive Documents

For highly sensitive documents:

- make the user action explicit
- clearly identify what will be shared
- avoid hidden extra attachments
- avoid broad default filenames containing sensitive personal information
- apply product/legal privacy requirements
- consider confirmation UI if the product requires it

Do not make unsupported legal claims based only on plugin behavior.

# Local Paths

Do not intentionally expose internal file-system paths as share text:

```text
/data/user/0/com.example/cache/private.pdf
```

For files, let the plugin/platform expose the appropriate shareable file mechanism.

Android uses content URIs for receiver access rather than expecting the destination to read your private raw path.

---

# Temporary Sensitive Exports

If a temporary export contains sensitive data:

- use an app-owned temp directory
- give it the shortest useful lifetime
- clean it at logout where appropriate
- clean old exports periodically
- do not retain unnecessary historical copies

Remember that a selected receiver can persist its own copy permanently.

# When a Share Service Helps

A lightweight service becomes useful when the application needs:

- privacy checks
- platform fallback policy
- export caching
- consistent filename/MIME mapping
- duplicate-call guard
- analytics
- unit testing
- centralized error mapping

Example interface:

```dart
abstract interface class AppShareService {
  Future<ShareResult> share(
    ShareParams params,
  );
}
```

Implementation:

```dart
import 'package:share_plus/share_plus.dart';

final class SharePlusService
    implements AppShareService {
  SharePlusService({
    SharePlus? sharePlus,
  }) : _sharePlus =
           sharePlus ??
           SharePlus.instance;

  final SharePlus _sharePlus;

  bool _inFlight = false;

  @override
  Future<ShareResult> share(
    ShareParams params,
  ) async {
    if (_inFlight) {
      return ShareResult.unavailable;
    }

    _inFlight = true;

    try {
      return await _sharePlus.share(
        params,
      );
    } finally {
      _inFlight = false;
    }
  }
}
```

Use the in-flight guard only when serializing the application's own share interaction is appropriate.

Do not globally block unrelated independent windows/features without reason.

# Duplicate Share Sheets

Common causes:

- rapid double tap
- two event listeners
- repeated state transition
- a callback fired twice
- multiple buttons invoking the same async flow
- lack of in-flight state

Use a simple preparation/share state.

# Stateful Button Example

```dart
import 'package:flutter/material.dart';
import 'package:share_plus/share_plus.dart';

class ShareTextButton extends StatefulWidget {
  const ShareTextButton({
    required this.text,
    super.key,
  });

  final String text;

  @override
  State<ShareTextButton> createState() =>
      _ShareTextButtonState();
}

class _ShareTextButtonState
    extends State<ShareTextButton> {
  bool _sharing = false;

  Future<void> _share(
    BuildContext buttonContext,
  ) async {
    if (_sharing) {
      return;
    }

    setState(() {
      _sharing = true;
    });

    try {
      final Rect? origin =
          shareOriginForContext(
        buttonContext,
      );

      final ShareResult result =
          await SharePlus.instance.share(
        ShareParams(
          text: widget.text,
          sharePositionOrigin: origin,
        ),
      );

      if (!mounted) {
        return;
      }

      if (result.status ==
          ShareResultStatus.dismissed) {
        // Ordinary cancellation. No error UI.
        return;
      }
    } catch (error) {
      if (!mounted) {
        return;
      }

      ScaffoldMessenger.of(context)
          .showSnackBar(
        const SnackBar(
          content: Text(
            'Unable to open sharing.',
          ),
        ),
      );
    } finally {
      if (mounted) {
        setState(() {
          _sharing = false;
        });
      }
    }
  }

  @override
  Widget build(BuildContext context) {
    return Builder(
      builder: (
        BuildContext buttonContext,
      ) {
        return FilledButton.icon(
          onPressed: _sharing
              ? null
              : () => _share(
                    buttonContext,
                  ),
          icon: _sharing
              ? const SizedBox.square(
                  dimension: 16,
                  child:
                      CircularProgressIndicator(
                    strokeWidth: 2,
                  ),
                )
              : const Icon(Icons.share),
          label: Text(
            _sharing
                ? 'Opening…'
                : 'Share',
          ),
        );
      },
    );
  }
}
```

For Web, do not insert lengthy asynchronous generation into `_share()` before the final `SharePlus` call if native Web Share is required.

After an `await`, the initiating widget may no longer exist.


before:

- showing SnackBars
- navigating
- updating UI

The share operation itself can remain active outside the widget lifecycle, but UI interactions cannot safely use a disposed context.

# Performance Rules — HIGH PRIORITY

## 1. Prefer path-backed files for existing large files

Mechanism avoided:

```text
disk -> Dart bytes -> temp disk
```

Path-backed:

```text
disk -> native share path
```

with platform-specific processing.

Android still copies into its share cache.

---

## 2. Never `readAsBytes()` solely to create `XFile.fromData` for an existing file

This adds:

- Dart heap
- garbage-collection pressure
- disk write
- possibly another Android disk copy

---

## 3. Do not generate content from `build()`

Bad:

```dart
Widget build(BuildContext context) {
  final bytes = generatePdf();

  ...
}
```

Why:

Flutter can rebuild for reasons unrelated to sharing.

---

## 4. Generate on explicit demand

For inexpensive generation:

```text
tap
 -> generate
 -> share
```

For expensive Web generation:

```text
prepare
 -> ready
 -> explicit Share tap
```

---

## 5. Cache expensive immutable exports when useful

Mechanism avoided:

```text
repeated PDF/image/video generation
```

Only cache when:

- repeated share is plausible
- source has not changed
- privacy permits local retention

---

## 6. Avoid excessive pre-generation

Do not create a 100 MB report at startup merely because a Share button exists somewhere in the app.

This harms:

- startup time
- disk
- CPU
- battery

---

## 7. Keep MIME accurate

This improves receiver filtering and avoids fallback to overly broad target matching.

---

## 8. Keep filenames meaningful

This avoids receiver confusion and makes exports understandable.

---

## 9. Keep attachment count reasonable

Every file can add:

- file-system checks
- Android copying
- URI grants
- browser byte buffers
- receiver processing

---

## 10. Avoid unrelated mixed MIME attachments

Android may have to advertise:

```text
*/*
```

reducing compatibility.

---

## 11. Compress only when useful

Compression trades:

```text
CPU
```

for:

```text
smaller disk/network/receiver payload
```

Measure based on file type and product fidelity.

---

## 12. Offload measured CPU-heavy generation

Move expensive pure computation off the UI isolate only when it causes actual frame jank.

Do not move platform UI/plugin invocation to a worker isolate.

---

## 13. Do not optimize around the tiny Dart method call

The expensive path is usually:

```text
generation
serialization
byte materialization
file I/O
native preview work
browser file creation
```

not obtaining `SharePlus.instance`.

---

# Reliability Rules

1. Verify a file still exists before sharing if its lifecycle is uncertain.
2. Give files correct extensions/MIME types.
3. Do not overlap multiple share sheets from one action.
4. Treat dismissal as normal.
5. Treat unavailable result as informational.
6. Recompute iPad/macOS origin after long asynchronous work.
7. Check `context.mounted` before UI work after `await`.
8. Keep Web share directly tied to user activation.
9. Do not depend on receiver-specific behavior.
10. Do not use result success as delivery confirmation.
11. Clean application-owned sensitive exports.
12. Do not assume plugin-created temp files disappear immediately.
13. Offer explicit fallbacks for unsupported platforms.
14. Test release builds as well as debug builds.
15. Validate target receiver applications that matter to the product.

A correct share intent can still produce unexpected target behavior.

Examples:

```text
email app accepts subject + attachment
social app ignores subject
messenger accepts image but discards accompanying text
app does not support multiple files
app refuses generic MIME
```

Do not write target-specific guarantees unless:

- the target documents them
- you use its dedicated SDK
- you test the supported versions

# Platform Permissions

`share_plus` itself does not require a generic "share permission."

Do not request permissions just because a share sheet will be shown.

Permissions belong to how the content was acquired.

Example:

```text
user picks photo
 -> picker/media permission model

app shares already-accessible photo
 -> share_plus share mechanism
```

These are separate.

---

# Android Scoped Storage

Modern Android scoped storage is compatible with current `share_plus` because the plugin shares copied cache content through `FileProvider` content URIs.

Do not implement obsolete:

```text
file:// URI exposure
WRITE_EXTERNAL_STORAGE
broad shared-storage copy
```

solely to make sharing work.

---

# Apple Sandbox

Application-private files can be handed to the system share controller as file URLs.

You do not need to move every app-private export into a globally readable directory.

The system/receiver handoff owns access according to the platform share mechanism.

Files acquired through other Apple APIs may have separate security-scoped-access lifecycle requirements; that is a file-acquisition concern, not something `share_plus` itself automatically solves.

---

# Accessibility and UX

Sharing-specific UX SHOULD:

- use a clear label such as "Share"
- show preparation progress for expensive exports
- disable duplicate taps while preparing/opening
- allow ordinary dismissal without alarm
- distinguish "Download" from "Share" on Web fallback when semantics matter
- provide alternative action if a platform cannot share the requested payload

Do not overload the UI with technical platform details unless the fallback changes user intent.

# Debugging Guide

| Symptom | Likely Cause | How to Verify | Fix |
|---|---|---|---|
| Share sheet never appears | Invalid params, platform failure, plugin registration | Catch/log exception, test minimal text share | Fix plugin/config/input |
| `ArgumentError` before native call | Empty/no payload or text+URI conflict | Inspect `ShareParams` | Supply valid combination |
| iPad share points to center | No valid `sharePositionOrigin` | Inspect RenderBox rect | Pass actual button rect |
| Old iPad version crashes | Older `share_plus` origin behavior | Check lockfile/changelog | Upgrade or provide valid origin |
| iPad origin invalid after export | Layout changed during async work | Recompute after `await` | Check mounted + fresh RenderBox |
| File missing in sheet | File gone/unreadable | Check existence/path | Recreate/retain export |
| Wrong target apps shown | MIME wrong/generic | Inspect MIME | Use specific correct MIME |
| No target accepts multiple files | Receiver limitation/mixed MIME | Test one file / same-type files | Split share or use target SDK |
| Text disappears when file shared | Receiver ignores combined content | Test target separately | Share file or text separately |
| Subject ignored | Receiver does not honor subject | Test email vs target | Treat as best-effort |
| Web does nothing | Web Share unavailable, no transient activation, policy/security | Browser console, HTTPS, direct button call | Use explicit user gesture/fallback |
| Web downloads file instead | Native Web Share unavailable/failed | Inspect browser support | Explain fallback or disable it |
| Web opens email composer | Native text share unavailable/failed | Inspect browser support | Accept email fallback or disable it |
| Web file share causes memory spike | All files read into memory | Profile heap/file sizes | Smaller/fewer files or URL/download UX |
| Native memory spike sharing image | Huge image decode/preview or generated bytes | Profile image dimensions | Resize/compress if acceptable |
| Dart memory spike | `readAsBytes`/`XFile.fromData` on large file | Heap profile/code search | Use path-backed XFile |
| Android temporary storage doubles | Android share-cache copy | Inspect cache size | Expected current behavior; reduce file size/count |
| Temporary files accumulate | `XFile.fromData` repeated | Inspect temp dir | Explicit app-owned temp lifecycle |
| Filename is UUID | Pathless generated file without override | Inspect params | Set `fileNameOverrides` |
| Override doesn't rename native existing file | Current native path is already fixed | Inspect actual path name | Create export with correct real filename |
| Linux file share throws | Unsupported | Check platform | Offer Save/Email link |
| Old Windows file share throws | Native share UI unavailable | Check Windows version | Offer Save/email fallback |
| Duplicate share sheets | Double taps/listeners | Instrument invocation count | In-flight guard |
| Result is `unavailable` | Platform lacks action result/fallback used | Check platform | Treat as valid non-result |
| Success but recipient got nothing | Receiver failed after target selection | Reproduce target-specific behavior | Do not use result as delivery confirmation |
| Receiver app absent | Not installed/not registered for MIME | Inspect system share targets | Cannot force generic receiver |
| Release-only MissingPluginException | Plugin registration/build integration problem | Test minimal current package example/release | Fix Flutter/native build integration |
| URI preview absent outside iOS | Special URI metadata is iOS-specific | Compare platform docs | Use text or target-specific integration |

# Anti-Patterns

## Anti-pattern: Deprecated static API

### Bad

```dart
Share.share(
  'Hello',
);
```

### Why

Deprecated since the SharePlus refactor.

### Preferred

```dart
SharePlus.instance.share(
  ShareParams(
    text: 'Hello',
  ),
);
```

---

## Anti-pattern: Assume identical platform features

### Bad

```text
Linux will share this PDF because pub.dev says Linux is supported.
```

### Why

Linux supports package text/URI fallback but not files.

### Preferred

Use capability-aware fallback.

---

## Anti-pattern: Old iPad rule repeated unconditionally

### Bad

```text
sharePositionOrigin is omitted => current share_plus always crashes.
```

### Why

13.3.0 introduced a center fallback.

### Preferred

Provide accurate origin for UX and treat omission behavior as version-sensitive.

---

## Anti-pattern: Ignore iPad origin completely

### Why

Even with current fallback, the popover anchors poorly.

### Preferred

Use the triggering widget's real rectangle.

---

## Anti-pattern: Generate large PDF in `build()`

### Bad

```dart
Widget build(BuildContext context) {
  final pdf = generateHugePdf();
  ...
}
```

### Why

Rebuilds can repeat CPU/memory work.

### Preferred

Generate from explicit application action.

---

## Anti-pattern: Read existing large file into bytes

### Bad

```dart
final bytes =
    await File(path).readAsBytes();

final file = XFile.fromData(bytes);
```

### Why

Duplicates a file into Dart memory and then temporary storage.

### Preferred

```dart
XFile(path)
```

---

## Anti-pattern: Call `XFile.fromData` for every file

### Why

Pathless files must be materialized.

### Preferred

Use it only for genuinely generated in-memory content.

---

## Anti-pattern: Claim path-backed Android sharing is zero-copy

### Why

Android currently copies files to the plugin share cache.

### Preferred

Describe it as Dart-memory efficient, not zero-copy.

---

## Anti-pattern: Recreate export every rapid tap

### Why

Repeated encoding/file I/O.

### Preferred

Cache stable export while source version remains unchanged.

---

## Anti-pattern: Wrong MIME

### Bad

```text
.pdf as image/png
```

### Why

Targets may disappear or mis-handle the file.

### Preferred

Correct MIME + extension.

---

## Anti-pattern: Use only extension and ignore known MIME

### Why

Inference can fail and fall back to generic binary.

### Preferred

Supply MIME when known.

---

## Anti-pattern: Assume `fileNameOverrides` renames every native file

### Why

Current method-channel implementation does not rename an already path-backed file.

### Preferred

Create the native export with the final desired filename.

---

## Anti-pattern: Assume `subject` works everywhere

### Why

Receiver applications decide whether to use it.

### Preferred

Treat as optional metadata.

---

## Anti-pattern: Share success means delivery

### Bad

```dart
if (result.status ==
    ShareResultStatus.success) {
  markMessageDelivered();
}
```

### Why

Success normally only describes share-sheet interaction.

### Preferred

Use backend/domain acknowledgement.

---

## Anti-pattern: Dismissal shown as failure

### Why

User intentionally canceled.

### Preferred

Silently return or show neutral UX.

---

## Anti-pattern: Retry a dismissal automatically

### Why

It reopens UI the user just closed.

### Preferred

Wait for another explicit Share action.

---

## Anti-pattern: Share access token

### Bad

```dart
ShareParams(
  text: session.accessToken,
);
```

### Why

Credential disclosure.

### Preferred

Never expose secrets through sharing.

---

## Anti-pattern: Long-lived private URL by default

### Why

Recipient can forward it and access remains valid.

### Preferred

Select attachment or appropriately scoped/expiring URL.

---

## Anti-pattern: Sensitive temp exports never cleaned

### Why

Private data remains on disk.

### Preferred

App-owned temp lifecycle.

---

## Anti-pattern: Delete entire app temp root

### Why

Other components may use it.

### Preferred

Clean only your own export directory.

---

## Anti-pattern: Assume Web Share in every browser

### Why

Web Share has limited availability.

### Preferred

Runtime capability + tested fallback.

---

## Anti-pattern: Launch Web Share from timer/background callback

### Why

No transient user activation.

### Preferred

Explicit button click.

---

## Anti-pattern: Long Web export after final Share click

### Why

Can consume transient activation before `navigator.share`.

### Preferred

Prepare first, then require explicit Share click.

---

## Anti-pattern: Silent Web download called "share"

### Why

Download and share are different user actions.

### Preferred

Label fallback honestly or disable it.

---

## Anti-pattern: Multiple share calls in flight

### Why

Duplicate UI; Android result behavior intentionally degrades overlapping calls to avoid deadlock.

### Preferred

Simple per-action in-flight guard.

---

## Anti-pattern: Heavy generation on UI isolate without measurement

### Why

Can cause frame jank.

### Preferred

Profile first; offload genuinely expensive pure CPU work.

---

## Anti-pattern: Obsolete Android storage permissions

### Why

Current plugin uses app cache and `FileProvider`.

### Preferred

Request only permissions required by your content-acquisition flow.

---

## Anti-pattern: Manual old FileProvider setup

### Why

Current share plugin owns its provider mechanism.

### Preferred

Let `share_plus` configure its sharing implementation.

---

## Anti-pattern: Test only Android emulator

### Why

Receiver ecosystem and inter-app handoff are incomplete.

### Preferred

Physical-device and real-target testing.

---

## Anti-pattern: Ignore iPad

### Why

Popover behavior is distinct.

### Preferred

Explicit iPad physical test.

---

## Anti-pattern: Trust third-party target compliance

### Why

The receiving app owns final interpretation.

### Preferred

Test important targets and use dedicated SDKs for hard requirements.

---

# Decision Framework

## Existing local file?

Use:

```dart
XFile(
  path,
  mimeType: knownMime,
)
```

Avoid reading it into bytes.

---

## Small generated bytes?

Use:

```dart
XFile.fromData(...)
```

with:

```dart
fileNameOverrides
```

when temporary materialization is acceptable.

---

## Large generated attachment?

Prefer:

```text
generate
 -> explicit temporary file
 -> path-backed XFile
```

so:

- peak Dart memory is controlled
- filename is predictable
- cleanup is controlled
- repeated sharing can reuse export

---

## Hosted content is the actual product experience?

Share the URL.

---

## Recipient needs a standalone attachment?

Download/generate the local file, then share it.

---

## Private hosted file?

Choose deliberately between:

```text
signed URL
```

and:

```text
download + attachment
```

based on expiry/privacy/recipient requirements.

---

## Web Share unavailable?

Choose explicitly:

```text
download fallback
email fallback
copy link
manual download button
unsupported message
```

Do not pretend those are equivalent.

---

## Linux file?

Use an application-specific export/save alternative.

---

## Need guaranteed post to one social network?

Generic OS sharing is probably the wrong contract.

Use that platform's official integration if it offers one and product requirements demand certainty.

# Final Instructions for AI Coding Agents

Before implementing or modifying sharing:

1. inspect the installed `share_plus` version
2. identify all product platforms
3. identify the actual share payload
4. determine whether an attachment or URL is the correct semantic choice
5. inspect current platform capability
6. estimate realistic payload size
7. avoid unnecessary byte materialization
8. choose MIME and filename deliberately
9. determine temporary-file ownership
10. provide accurate iPad/macOS share origin
11. preserve Web user activation
12. decide Web fallback explicitly
13. implement one in-flight share action
14. treat result as UI interaction only
15. review content for secrets/sensitive data
16. test the exact target platforms and important receiver applications

Optimize in this order:

```text
correct sharing semantics
      |
      v
platform compatibility
      |
      v
privacy/security
      |
      v
payload generation cost
      |
      v
memory materialization
      |
      v
disk/temp-file behavior
      |
      v
receiver compatibility
      |
      v
plugin-call overhead
```

For large existing native files, the preferred flow is usually:

```text
existing file
     |
     v
path-backed XFile
     |
     v
SharePlus
     |
     v
platform-specific file handoff
```

not:

```text
existing file
     |
     v
readAsBytes()
     |
     v
XFile.fromData()
     |
     v
temporary file
     |
     v
SharePlus
```

For expensive Web exports, prefer:

```text
Prepare
   |
   v
content ready
   |
   v
explicit user Share click
   |
   v
navigator.share via share_plus
```

rather than performing long asynchronous preparation after the final user activation.

The best `share_plus` architecture is usually simple:

```text
explicit user action
      |
      v
prepare/reuse correct payload
      |
      v
validate privacy + platform semantics
      |
      v
SharePlus.instance.share(...)
      |
      v
treat OS result as best-effort interaction feedback
```

Do not add architecture merely for ceremony.

Do add a service boundary when it centralizes real concerns such as:

- export caching
- privacy rules
