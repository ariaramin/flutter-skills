# flutter_lints & Dart Static Analysis Engineering Skill

## Purpose

Use this skill when configuring, reviewing, enforcing, debugging, migrating, or extending static analysis in production Flutter/Dart repositories that use `flutter_lints`.

Treat static analysis as an **engineering-quality system**, not as formatting theater or a contest to enable the largest possible lint set.

Use this skill to make senior-level decisions about:

- selecting the correct `flutter_lints` version;
- configuring `analysis_options.yaml`;
- understanding the effective inherited lint set;
- adding high-value project-specific rules;
- enabling strict type-analysis modes;
- deciding whether a rule should be fixed, overridden, or locally suppressed;
- handling generated code;
- applying different policy to apps, packages, tests, and examples;
- coordinating analysis across monorepos;
- enforcing analysis in CI;
- using `dart fix` safely;
- diagnosing analyzer/IDE/CI mismatches;
- migrating lint policy across Flutter and Dart SDK releases;
- maintaining a high signal-to-noise ratio.

### Current stable baseline

The current published `flutter_lints` release is:

```yaml
dev_dependencies:
  flutter_lints: ^6.0.0
```

`flutter_lints 6.0.0` requires Dart `^3.8.0`. Its release notes associate that baseline with Flutter 3.32 / Dart 3.8. Current Flutter project templates still generate `flutter_lints: ^6.0.0`.

The repository's current `main` branch already contains unreleased `NEXT` changes raising its development baseline to Flutter 3.38 / Dart 3.10. Do not infer released package compatibility from repository `main`; use the installed package/version or matching tag.

# What flutter_lints Does

`flutter_lints` is an official Flutter-team configuration package containing a recommended lint set for Flutter:

- applications;
- packages;
- plugins.

It does not contain runtime library functionality. The stable package consists of configuration and a dependency on the Dart team's `lints` package. Its `flutter.yaml` includes:

```yaml
include: package:lints/recommended.yaml
```

and then adds Flutter-specific rules.

The Dart analyzer evaluates these lints and surfaces their diagnostics through:

- Dart/Flutter IDE integrations;
- `flutter analyze`;
- `dart analyze`;
- Analysis Server;
- compatible analyzer tooling.

Flutter projects generated by `flutter create` have used `flutter_lints` by default since Flutter 2.3. Current templates continue to include:

```yaml
include: package:flutter_lints/flutter.yaml
```



---

# What flutter_lints Does NOT Do

Do not treat `flutter_lints` as:

- a Dart compiler;
- a formatter;
- a type system;
- a unit-test framework;
- an integration-test framework;
- an architecture dependency checker;
- a security scanner;
- a dependency-vulnerability scanner;
- a secret scanner;
- a performance profiler;
- a runtime assertion system;
- proof that code is correct;
- proof that code is secure;
- proof that code is fast.

The analyzer can detect many errors and likely problems before execution, but static analysis and linting remain only part of engineering validation.

A lint-clean application can still:

- crash;
- have incorrect state transitions;
- leak secrets;
- have race conditions;
- violate product requirements;
- perform poorly;
- be inaccessible;
- misuse backend authorization;
- contain untested edge cases.

# Current Rule Set — Inspect Before Assuming

## Stable `flutter_lints 6.0.0`

The stable package's `flutter.yaml` directly enables these ten Flutter-specific rules:

```yaml
linter:
  rules:
    - avoid_print
    - avoid_unnecessary_containers
    - avoid_web_libraries_in_flutter
    - no_logic_in_create_state
    - prefer_const_constructors_in_immutables
    - sized_box_for_whitespace
    - sort_child_properties_last
    - use_build_context_synchronously
    - use_full_hex_values_for_flutter_colors
    - use_key_in_widget_constructors
```



Classify them by engineering purpose:

| Rule | Primary purpose |
| --- | --- |
| `avoid_print` | Production logging/hygiene |
| `avoid_unnecessary_containers` | Widget-tree readability/simplification |
| `avoid_web_libraries_in_flutter` | Cross-platform correctness |
| `no_logic_in_create_state` | Flutter lifecycle correctness |
| `prefer_const_constructors_in_immutables` | Immutable API design |
| `sized_box_for_whitespace` | Clear widget intent |
| `sort_child_properties_last` | Widget construction readability |
| `use_build_context_synchronously` | Async lifecycle safety |
| `use_full_hex_values_for_flutter_colors` | Color-value correctness |
| `use_key_in_widget_constructors` | Widget API/reconciliation support |

The package inherits the Dart team's complete recommended rule set. `package:lints/recommended.yaml` itself includes the `core` set.

With `lints 6.0.0` specifically resolved, the hierarchy contains:

```text
35 core rules
+
56 additional recommended rules
+
10 flutter_lints-specific rules
=
101 unique active rules
```

Do not duplicate those rules manually.

## Important transitive-version nuance

`flutter_lints 6.0.0` declares:

```yaml
dependencies:
  lints: ^6.0.0
```

rather than an exact `6.0.0` dependency.

The current stable `lints` release is `6.1.0`, which added `use_null_aware_elements` and updated its recommended configuration. Therefore two repositories both declaring:

```yaml
flutter_lints: ^6.0.0
```

can have slightly different effective rule sets if their resolved `lints` versions differ.

Always inspect:

```text
pubspec.yaml
+
pubspec.lock / workspace lock
+
resolved package graph
```

when diagnosing a rule that exists on one machine but not another.

Useful command:

```sh
flutter pub deps
```

Do not assume the top-level `flutter_lints` version tells the entire effective rule set.

---

## `strict_top_level_inference` is already included

`lints 6.0.0` added `strict_top_level_inference` to its core set. It flags declarations where omitted types fall back to `dynamic` because top-level/member inference cannot determine a type.

This is **not** the same as:

```yaml
analyzer:
  language:
    strict-inference: true
```

The lint is narrower.

Do not disable strict analyzer modes because you see the word `strict` in `strict_top_level_inference`; they enforce different policies.

---

## The old const-heavy Flutter baseline is obsolete

Current `flutter_lints` no longer includes:

```text
prefer_const_constructors
prefer_const_declarations
prefer_const_literals_to_create_immutables
```

They were removed in `flutter_lints 5.0.0`.

`prefer_const_constructors_in_immutables` remains.

The Flutter/Dart lint discussion behind this change reported insufficient real-world performance evidence to justify the development noise produced by the three broad const rules.

Therefore do not tell a modern Flutter repository:

> “Flutter best practice requires `prefer_const_constructors` because flutter_lints enables it.”

It does not.

Teams may still enable those rules deliberately, but that is **project policy**, not current Flutter default policy.

# Core Principles

1. **Start with the official Flutter lint set.**
2. **Keep `analysis_options.yaml` in version control.**
3. **Treat lint configuration as repository engineering policy.**
4. **Optimize for signal, not rule count.**
5. **Understand a diagnostic before suppressing it.**
6. **Prefer fixing code over ignoring diagnostics.**
7. **Prefer a local suppression over weakening project-wide policy for one exception.**
8. **Prefer a project-wide policy change when the rule itself is unsuitable everywhere.**
9. **Do not edit generated code manually to satisfy lints.**
10. **Do not exclude production source merely to make analysis pass faster.**
11. **Do not blindly enable every available lint.**
12. **Do not blindly enable every strict analyzer mode during a large migration.**
13. **Do not conflate lint rules with type-system diagnostics.**
14. **Do not use linting as a substitute for tests.**
15. **Do not use linting as proof of architecture correctness.**
16. **Do not use linting as proof of security.**
17. **Do not use linting as a runtime-performance strategy.**
18. **Treat Flutter/Dart/lint upgrades as migrations.**
19. **Remove obsolete suppressions after migrations.**
20. **Keep IDE and CI SDK/configuration aligned.**
21. **Do not normalize permanent analyzer debt.**
22. **Prevent new lint debt while old debt is being removed.**

# Mental Model

Do not model the toolchain as one interchangeable “lint check.”

Use:

```text
Dart source
│
├── Dart language / type system
│   └── compile-time legality
│
├── Dart analyzer
│   ├── language/type diagnostics
│   ├── analyzer diagnostics
│   └── linter diagnostics
│       ├── package:lints
│       ├── package:flutter_lints
│       └── project-added rules
│
├── analyzer severity policy
│   ├── info
│   ├── warning
│   └── error
│
├── Dart formatter
│   └── formatting/layout only
│
├── tests
│   └── behavior verification
│
└── compiler/runtime
    └── actual program behavior
```

These layers interact but are not substitutes for one another.

```text
dart format
≠
flutter_lints
≠
flutter analyze
≠
flutter test
≠
runtime correctness
```

# Analyzer Errors, Warnings, Infos, Hints, and Lints

Current analyzer severity configuration has three levels:

```text
info
warning
error
```

plus `ignore` when suppressing a diagnostic through configuration.

Older Dart tooling and some Flutter command text may use the word **hint**. Do not configure a separate `hint` severity; current analyzer severity configuration uses `info`, `warning`, and `error`.

### Language/analyzer diagnostics

These originate from:

- Dart syntax;
- type-system rules;
- analyzer checks;
- SDK annotations;
- language semantics.

Examples include invalid assignments, dead code, or invalid null-aware operations.

### Lints

Lints are analyzer diagnostics produced only when their lint rule is enabled.

They can represent:

- likely bugs;
- API misuse;
- maintainability concerns;
- package hygiene;
- readability conventions;
- Flutter-specific practices.

Lints can have false positives and can disagree with other lint rules. Dart's own documentation explicitly warns about this.

# Default Setup

For a modern Flutter project, start small:

```yaml
include: package:flutter_lints/flutter.yaml
```

That is enough to activate the official set.

Current Flutter templates generate essentially this policy.

Add `flutter_lints` as a dev dependency:

```sh
flutter pub add dev:flutter_lints
```

or configure:

```yaml
dev_dependencies:
  flutter_lints: ^6.0.0
```

Use the version compatible with the repository's Dart/Flutter SDK rather than blindly copying the latest number.

# Production Baseline Example

A mature project might intentionally extend the baseline:

```yaml
include: package:flutter_lints/flutter.yaml

analyzer:
  language:
    strict-casts: true
    strict-raw-types: true

linter:
  rules:
    discarded_futures: true
    unawaited_futures: true
    unnecessary_ignore: true
```

This is **not** the universal recommended configuration.

Every addition above is a team policy decision that requires migration/noise evaluation.

# Include / Inheritance

## Single include

Standard:

```yaml
include: package:flutter_lints/flutter.yaml
```

Local configuration overrides inherited configuration.

---

## Multiple includes

Modern Dart also supports an ordered include list:

```yaml
include:
  - package:flutter_lints/flutter.yaml
  - team_options.yaml
```

Included files are applied in order, and the local `analysis_options.yaml` is applied last. Later configuration therefore overrides earlier configuration.

Use multiple includes only when the precedence is intentional.

Do not create:

```text
five lint packages
+
three local include files
+
unclear override order
```

and expect developers to understand the effective policy.

---

# Shared Configuration Pattern

For a large organization, prefer a clear chain:

```text
flutter_lints
↓
organization policy
↓
repository policy
↓
rare package-specific override
```

For example, an internal configuration package can export:

```yaml
include: package:flutter_lints/flutter.yaml

analyzer:
  language:
    strict-casts: true

linter:
  rules:
    unawaited_futures: true
    unnecessary_ignore: true
```

A project then includes the organization configuration rather than recreating it.

This is architecture guidance, not a `flutter_lints` requirement.

Tradeoffs include:

- centralized upgrades;
- consistent rules;
- reduced copy/paste;

versus:

- organization-wide coupling;
- coordinated migrations;
- version compatibility requirements.

# Rule Overrides

## Enabling an extra rule

Use map syntax when a file also needs to override inherited rules:

```yaml
include: package:flutter_lints/flutter.yaml

linter:
  rules:
    unawaited_futures: true
```

---

## Disabling an inherited rule

```yaml
include: package:flutter_lints/flutter.yaml

linter:
  rules:
    avoid_print: false
```

Do not disable a lint merely because:

```text
"there are too many violations"
```

First determine whether:

- the rule detects a real problem;
- the codebase needs migration;
- an automated fix exists;
- only one area requires an exception;
- the rule conflicts with deliberate repository policy.

Dart requires map syntax when enabling/disabling rules using boolean values; list and map syntax cannot be mixed within the same `rules:` entry.
